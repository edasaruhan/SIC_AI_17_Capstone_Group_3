# 1. PROJECT IDENTITY

Project name:

**ARGUS AI — Graph-Based Financial Crime and Account Network Intelligence**

Core idea:

> Move from suspicious transactions to suspicious networks.

ARGUS is a human-in-the-loop financial crime decision-support prototype for digital banks and small/medium-sized banks.

The system should not simply assign a fraud score to isolated transactions. It should model transfers as a directed account network and evaluate whether graph information adds measurable value over strong transaction-level baselines.

The project should ultimately allow an analyst to:

1. see a ranked investigation queue,
2. open a suspicious case,
3. inspect its local transaction network,
4. understand why it was flagged,
5. compare transaction-only and graph-aware models,
6. review evidence before making a human decision.

ARGUS must never automatically declare a person/account guilty or recommend punitive action.

Use language such as:

- suspicious network candidate,
- elevated investigation priority,
- unusual transfer pattern,
- evidence requiring human review.

Never use unsupported language such as:

- money launderer,
- criminal,
- guilty,
- block this account,
- freeze the account.

# 3. NON-NEGOTIABLE SCIENTIFIC RULES

## 3.1 No fabricated outputs

Never manually type model performance numbers into Markdown, notebooks, dashboards, reports, or code.

All metrics must be produced by code.

All figures must be generated by code.

All comparison tables must be generated from saved experiment outputs.

If the full experiment cannot run because the dataset is unavailable or hardware is insufficient:

- build the pipeline,
- add validation/tests,
- run a small smoke/demo dataset where possible,
- clearly mark full-dataset experiments as pending.

## 3.2 Prevent temporal leakage

The dataset contains timestamped financial transactions.

DO NOT use a naive random row-level train/test split as the primary evaluation strategy.

Implement chronological:

- train
- validation
- test

splits.

At transaction time `t`, any historical feature must only use information strictly prior to `t`.

Examples:

- previous transaction count,
- rolling volume,
- previous counterparties,
- historical degree,
- transaction burst statistics.

Future observations must never contribute to a feature describing an earlier transaction.

Create automated leakage tests.

## 3.3 Preserve account identity correctly

A bank account identifier must be globally represented as a composite identifier.

Use:

`bank_id + account_id`

for sender and receiver account IDs so identical account strings in different banks are not incorrectly merged.

## 3.4 Keep test set untouched

Do not tune on the final test set.

Workflow:

train -> validation/model selection -> refinement -> freeze -> final test.

The final test evaluation must happen only after the model/refinement decisions are locked.

## 3.5 Evaluate class imbalance correctly

The positive laundering class is extremely rare.

Accuracy must NOT be presented as the main performance metric.

Primary evaluation must include:

- PR-AUC
- Recall@K
- Precision@K
- F1
- False Positive Rate
- alert volume

ROC-AUC may be shown as a secondary metric only.

Thresholds should be interpreted in terms of operational alert volume and analyst capacity.

# 14. PHASE 8 — GRAPHSAGE

Only begin after the baseline and graph-feature experiments work.

Primary GNN:

**GraphSAGE**

Important target-design rule:

The IBM dataset provides transaction-level laundering labels.

Do not invent unsupported account-level fraud labels merely to make node classification easier.

Prefer a transaction/edge-level prediction design.

Recommended architecture:

1. create account node embeddings with GraphSAGE,
2. obtain sender embedding,
3. obtain receiver embedding,
4. combine embeddings with transaction features,
5. classify the transaction using an MLP / edge classifier.

Conceptually:

```text
sender node -> GraphSAGE -> z_sender
receiver node -> GraphSAGE -> z_receiver

[z_sender, z_receiver, transaction_features]
                    |
                    v
                   MLP
                    |
                    v
        P(transaction is laundering)
```

The GNN must use the same chronological evaluation logic.

Prevent graph leakage from test-period edges into training representations.

Document the exact graph construction used for each split.

If full-scale GraphSAGE is too expensive, implement:

- deterministic sampled training,
- mini-batch neighborhood sampling,
- a clearly documented scalable subset experiment.

Never pretend a subset experiment is a full-data result.

# 30. WORKING METHOD

Follow this process.

## Step 1 — Audit

Before changing files:

- inspect the repository,
- identify existing documents,
- identify current code,
- identify missing components,
- write a concise implementation plan.

Do not blindly rewrite the repository.

## Step 2 — Build vertically

Implement one working path at a time.

Preferred sequence:

data load
-> validation
-> preprocessing
-> split
-> features
-> baseline
-> metrics
-> graph
-> graph-enhanced model
-> refinement
-> GNN
-> cases
-> Streamlit

## Step 3 — Test after every module

Run the relevant tests.

Do not accumulate dozens of untested files.

## Step 4 — Keep artifacts reproducible

Every experiment should save:

- config,
- timestamp/run ID,
- parameters,
- metrics,
- plots.

## Step 5 — Update README continuously

README must always reflect current reality.
